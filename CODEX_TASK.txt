# 給 Codex 的完整開發任務｜熱血少年拍攝工作管理系統

**任務性質：直接接手現有專案、修好並完成可正式使用的免費雲端網頁版。不要重新從零做一個示範網站。**

## 0. 必讀專案與現況

- 現有免費網站（目前主要是展示介面）：https://rexue-photo-workspace-free.onrender.com
- GitHub 程式分支（以此為唯一雲端版主線）：https://github.com/cs619et-hash/rexue-photo-assistant-test/tree/rexue-workspace-firebase-free
- 專案位置：`web/index.html`、`web/style.css`、`web/app.js`、`web/firebase-config.js`、`firebase.json`、`firestore.rules`、`firestore.indexes.json`、`tests/`。
- 私人交接 ZIP 另含 `01_最新V5_免費雲端網頁版`、`02_舊版V4_2_本機程式參考`（Python / SQLite / Google Calendar 行程快照）和 `03_參考截圖`，供功能對照及安全遷移。
- Render 免費**靜態**網站已發布、GitHub 有自動部署；但目前 **Firebase Spark 專案、Google Auth、Firestore 資料庫、rules 未經確認完成，雙帳號真實同步與舊資料搬遷均未驗證**。不可把「展示模式能按鈕」宣稱為正式可用。
- 不動現有公開 `main` 分支上的其他攝影程式；只在 `rexue-workspace-firebase-free` 分支改動本專案。

## 1. 最高優先級，不可違反

1. **永遠維持每月 NT$0**：只用 Firebase **Spark** 與免費靜態 Hosting。絕對不升級 Blaze、不啟用付費功能、不加信用卡、不建立 Render 付費 Web Service 或磁碟。若免費方案無法實現某項功能，應改為免費可行作法並明確報告，不能擅自產生費用。
2. **永遠保留舊拍攝紀錄**：不要清空、覆寫或重設既有資料庫；不要刪除正式舊版的 `data`、SQLite、Google Calendar 紀錄。任何移轉先唯讀分析 → 備份 → 預覽差異 → 防重複匯入 → 驗證筆數，再寫入。正式資料和模擬資料徹底分開。
3. **網站更新不用下載**：延用現有固定網址，GitHub 發布完成後 F5/重新整理即可取得新介面。網站程式和 Firestore 紀錄分離；改版不能清空資料。
4. **兩位攝影師共用、各自獨立完成**：植先、植丞可同一天拍不同場、也能兩人同場；同一場在 UI 顯示一張卡片，各自有拍攝完成、交件完成、期限與操作紀錄。
5. **安全優先**：公開站台可以載入，但只有經核准的兩個 Google 帳號能存取團隊內部資料。部署、測試 Firestore Rules 後才放正式行程；不能用開放測試規則。不可把私人日曆快照、家長個資、SQLite、Google OAuth client secret、service account key 放進公開 GitHub。
6. **日期只顯示 YYYY/MM/DD（含星期可）**，不顯示時分秒；同一天可有多筆賽事。所有 UI 以台灣時區及本地日期計算，不得因 UTC 轉換錯一天。

## 2. 完成雲端登入、資料庫與部署（P0）

- 先檢查現存 Firebase 專案，不要重複建立；如無，建立 Spark 免費專案，註冊 Web App，啟用 Authentication Google 登入，限制網站授權網域。
- Cloud Firestore 使用安全規則 `firestore.rules`，必須進行 Firebase Emulator / Rules 單元測試，驗證未登入、陌生 Google 帳號、待核准申請者不能讀寫工作紀錄；正式成員可以讀寫被授權團隊的資料；跨團隊不洩露。
- 第一位攝影師建立團隊，第二位以團隊邀請碼申請加入；只有管理員能核准。更推薦採用不可猜測邀請碼、過期/撤銷機制，並避免未授權使用者列出團隊 ID。**不要以顯示姓名當身分驗證**，需綁定 Google Auth UID；第二個實際帳號需由本人授權測試。
- 使用 `onSnapshot` 或其他 Firestore 即時監聽，確保手機、桌機的已拍/待交/結案狀態同步；離線/網路失敗時要提示「尚未儲存」，不能假裝完成。
- 建立最小權限的資料模型，建議：賽事共用欄位（唯一來源 ID、拍攝日期、比賽名、組別、地點）與 **per-photographer assignments**（攝影師 UID、拍攝狀態、交件狀態、正式期限/預估期限、完成時間、更新者、更新時間）。保持原版相容性或撰寫可重複執行的無破壞遷移程式。
- 優先延續既有 Render 免費靜態站，或在完全免費、無需計費的前提下使用 Firebase Hosting；不可無故換網址。若 Firebase CLI 所需登入或瀏覽器授權無法自動完成，要指出唯一阻礙和最小手動步驟。
- 更新時必須有明確部署紀錄、公開網址、實際登入／資料寫入讀回測試。禁用假資料冒充真實同步。

## 3. 攝影師日常工作流程（P0）

### 首頁僅以三個主入口為核心

1. **接下來拍攝**：未確認拍攝完成的未來賽事，拍攝日期**由近到遠**；顯示日期、賽事全名、組別/隊伍、地點（有才顯示）、負責攝影師、距拍攝剩幾天。點一場就能一鍵標記「拍攝完成」。
2. **已拍待交件**：已人工確認拍完、尚未正式交件。依**正式交件期限**優先顯示即將到期的案件；逾期置頂並醒目提醒。若沒有正式期限只有「預估期限」，標成「預估」且**不可顯示正式逾期**。完成後一鍵「完成交件」。
3. **已完成交件**：只有已確認交件才可結案。最近完成的置前，保留拍攝日期、交件日期、攝影師及檢索能力；可以更正誤按，但需明確確認與操作紀錄。

**額外提醒（不是第四個搶畫面的主導覽）**：「日期已過、尚未確認拍攝」→ 待核對。遇颱風延期或取消時，可選延期/停拍，不可因日期到期自動判定拍完；延期要能直接修改日期，不需刪除重建。

### 每張工作卡片

- 第一視線：日期 → 賽事名 → 攝影師 → 最重要的狀態/天數 → **唯一明顯主按鈕**。
- 同場兩位攝影師合併一張賽事卡，下方依植先/植丞各一列操作。兩人的工作狀態及交件截止日**不互相連動**。即便只一人完成，也不能把整場誤算成兩人都完成。
- 可點開詳細內容調整日期、攝影師、期限、備註、場次、特殊情況；刪除、取消、進階操作放次要選單，重要操作有確認及復原機制。
- 不要在主清單顯示「照片篩選中、修圖中、照片進度百分比」等複雜分階段資訊；**只管拍攝完成與交件完成**，舊欄位資料不要硬刪。

### 篩選、搜尋、計數

- 頂部能一鍵切換「全部 / 植先 / 植丞」。按下三個狀態數字直接切換下面同一份工作清單，不要逼使用者找其他頁面。
- 搜尋支持賽事名稱、日期、組別/隊伍、地點；同一天可有多場；排序依各分類的操作邏輯。
- 主視覺統計是**賽事場數**，同場兩位只算一場；另可顯示「攝影師待交工作數」但標籤須清楚，避免重複計算。
- 除三主狀態外，應保留「全部紀錄」、「待核對」、「取消/延期」檢視，正常情況不遮擋主要頁面。

## 4. UI / UX 深度優化（P1，必須實作）

- 品牌感：深海軍藍／接近黑的底色、攝影黃點綴、乾淨銳利的字級層次、運動攝影工作站感。別放大幅照片或裝飾讓工作清單被擠出首屏。
- 電腦首頁清楚、手機首頁首屏就應看到**至少第一件真正待辦的工作**；操作按鈕好點、間距合適、無左右橫向卷軸。
- 卡片標題長短兼容、不要文字溢出；不能用只有顏色的方式表示緊急程度，也要有「剩 2 天／已逾期 1 天」文字。
- 使用一個主清單與醒目三分類；搜尋/攝影師切換固定易找。新增工作採少量必要欄位；日期預設今天且只要日期，沒有時段。
- 優化沒有資料、讀取中、網路中斷、登入逾時、帳號待核准等狀態及錯誤文案；提供明確下一步，不出現一大段技術錯誤。
- 電腦與 iPhone/Android 瀏覽器都要實測；避免只能用滑鼠才操作得到的功能。保留友善鍵盤操作、焦點樣式及基本無障礙標籤。
- 首頁不要放已拍天數、篩照片進度條、過多 KPI、過大封面或一大段說明，讓使用者 5 秒內知道下一步。

## 5. Google Calendar 安全匯入與維護（P1）

- 使用者的拍攝行程來源是 Google 日曆。**只匯入拍攝日期 `2026-09-01`（含）以後**的事件；比賽日期以日曆所在時區解析（台灣），對跨日、全天事件需正確拆分或保留所需每一天，避免日期錯位。
- 支援選擇要匯入的行事曆、預覽事件、勾選要匯入的場次、顯示重複/新增/改期/取消等差異後再確認；匯入只新增/安全合併，禁止蓋掉已拍/已交狀態。
- 同一 Google event ID + 日期 + 賽事識別維持可追溯來源與冪等匯入；遇到改期有提示，不可讓手動修正被下一次同步覆寫；已由使用者刪除/忽略的事件下次不能無故復活。
- 舊 `calendar_snapshot.json` 只是一份 **2026-10-28 靜態快照**，不是即時同步。優先完成穩定的匯入與防重複；若要自動同步，必須另行實作 Google Calendar OAuth 授權與 token 安全管理，且符合免費方案。不可以聲稱未做好的即時同步已完成。
- 支援安全匯入舊 V4.2 JSON / SQLite 資料（在**本機**做轉換，絕不放到公開 GitHub），先備份與核對攝影師 ID 到「植先/植丞」映射，避免名字對錯；不因沒有資料庫就假造既有完成紀錄。

## 6. 資料防護、錯誤預防與安全（P0 / P1）

- 成功登入不代表就有資料權限：必須經管理員核准。使用 Firestore Rules 限制讀寫，並測試不能讀寫其他團隊資料，避免使用者自己改 `ownerUid` 等欄位取得權限。
- 同場操作一人更新時不能覆寫另一人剛更新的狀態；應採欄位級更新或 Firestore 交易；寫入失敗要反映在 UI，支援再次嘗試。
- 要有備份/匯出 JSON、匯入前預覽和驗證、誤刪復原或軟刪除；必要時記錄更新者與更新時間，避免兩人互相改了不知道。
- 避免儲存或記錄家長個資與存取 token；公開站台不得外洩真實賽事資料、資料庫密鑰或未經授權的文件 URL。
- Firebase Spark 免費限額與功能限制要檢查、必要時提供可見提醒；不得在前端放任何 Admin SDK 私鑰。實際備份策略應考慮 Spark 方案限制。

## 7. 測試與驗收（不能只回覆「已完成」）

1. 靜態程式與本機單元測試通過，新增關鍵狀態轉換、排序、日曆冪等匯入、舊資料轉換測試。
2. Firestore Rules 測試：未登入、非成員、待審核、管理員、正式成員、跨團隊資料隔離、禁止非法更新。
3. 用**兩個真實已授權 Google UID** 在兩個裝置或獨立瀏覽器工作階段驗證：A 更新「拍攝完成」→ B 即時看見；B 更新交件→ A 即時看見；同場另一位攝影師狀態不被影響。
4. 測試不同日期、同一天不同場、同場雙人、延期、取消、日期已過待核對、預估期限不算逾期、過期排序、結案、重複匯入、手動刪除後再次同步的情形。
5. 檢查手機首屏、無橫向溢出、所有主要按鈕觸控可點、登入待審核及斷網提示。
6. 無資料遺失：移轉前後筆數對帳，既有完成狀態一筆不丟；若缺正式資料，明確標成尚待移轉，不得補造。
7. 同一個公開網址成功更新到新版本，確認不是展示模式，並附實際網站 URL、版本 Commit SHA、測試結果、待處理事項。

## 8. 執行方式與回報

- **直接檢查、修程式、跑測試、發布到原網址**。不要只給想法、教學或請使用者反覆下載 ZIP。
- 不要求使用者再回答已經講過的需求；不確定的細節採用安全且容易回復的合理預設。
- 只有 Google 授權、Firebase Console 人工驗證、真實雙帳號登入、付款等只能本人完成的外部操作，才精確請求最小的那一步。**絕對不要求付款或 Blaze**。
- 每次報告分成：**已實際完成**／**尚未完成**／**目前唯一阻礙**；不得用測試資料或 UI 模擬假裝資料同步已上線。

**最終體驗：植先、植丞每天只需要打開同一網址 → 看即將拍攝與待交件 → 拍完按一下 → 交件按一下；日曆、日期排序、倒數、同步與紀錄保護由系統完成。**
